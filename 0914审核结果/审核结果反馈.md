## 一、先说结论

当前项目不是“代码完全不能用”，而是处在 **已有 Android 探针可以运行，但交接包尚未安全并入主工程** 的阶段。

交接包中的 11 个纯 Java 核心类本身通过了 39 项检查，具有接入价值；主工程也已有截图、节点取字、日文 OCR、候选选择和悬浮卡片。但两边的数据模型和任务控制方式还没有统一，而且交接包缺少两份关键说明文档。现在若直接复制或覆盖，短期可能编译成功，长期容易形成两套模型或两套生命周期控制，出现重复 OCR、旧页面结果回写、正文选择丢失等问题。

建议先补齐事实和唯一流程，再做功能扩展。当前不应直接进入 DeepSeek 接入，也不应为了“看起来完成”创建第二套状态机或新的 Android 工程。

## 三、当前卡点

### 卡点 1：交接材料不完整

`manifest.sha256` 和 README 都引用以下文件，但当前副本没有正文：

- `core_modules/docs/另一台电脑接入指南.md`
- `core_modules/docs/模块地图与规则.md`

影响：缺少原作者设计的迁移顺序、模块对应关系和具体边界。现有源码仍能分析，但不能声称已经完整阅读正式交接说明，也不应凭文件名自行补写后冒充原文。

解决方式：优先从 Mac 原始目录或原始压缩包重新复制这两个文件。复制时建议直接使用 ZIP，并在 Windows 解压后用 `manifest.sha256` 核对，不通过聊天软件逐个改名。

### 卡点 2：《长期稳定版开发总方案》身份不明确

指定路径 `docs/长期稳定版开发总方案.md` 不存在。仓库根目录有 `sakurazaka_cli_development_plan.md`，功能上像主开发方案，但文件名和标题不同。

影响：无法确定交接包所说的“用户已确认长期方案”是不是当前仓库这份主方案，也无法判断是否还有更新版本未复制过来。

解决方式：由用户确认现有 `sakurazaka_cli_development_plan.md` 是否就是交接包所指的长期方案；如果不是，需要提供正确文件。

### 卡点 3：主工程和交接包存在两套相似数据模型

主工程已有：

- `capture.ProbeModels.Bounds`
- `capture.ProbeModels.TextFragment`

交接包又提供：

- `domain.model.Bounds`
- `domain.model.TextFragment`
- `domain.model.ChatMessage`
- `domain.model.PageToken`

两边不是简单的同名覆盖关系。主工程模型带有 provenance、warnings、decisionReason、displayText 等诊断信息；交接模型增加了 confidence、traversalIndex、消息边界和页面身份约束。

影响：直接替换会破坏现有服务和测试；长期保留两套又可能在转换时丢失来源、警告、人工选择或坐标信息。

解决方式：先设计一个单向、可测试的适配边界，保留主工程采集证据，再逐步把稳定的 domain 模型变成唯一业务契约。这个技术方案可以由开发代理根据代码自行完成，不需要用户选择 Java 类名。

### 卡点 4：生命周期负责人尚未真正统一

生产服务目前使用 `ProbeLogic.RequestGate`，而 `CaptureCoordinator` 尚未用于生产。两者都处理请求开始、失效、结束和忙碌状态，只是覆盖范围不同。

影响：若直接再加入翻译流程或新协调器，可能出现：

- 页面已经切换，旧 OCR 或旧译文仍更新卡片；
- 用户关闭卡片后，迟到回调重新打开结果；
- 上一任务实际未结束，但新任务已开始；
- 旧任务的完成回调错误释放新任务占用；
- Bitmap、OCR 和网络请求由不同状态源管理。

解决方式：以现有 `CaptureCoordinator` 为迁移目标，把 `RequestGate` 的生产行为、页面身份、物理任务、结果状态和关闭状态逐项合并，并同步迁移测试。旧路径没有退役前，不允许两边并行触发 OCR 或网络。

### 卡点 5：当前 BODY 只是正文候选，不是已确认消息

现有 `TextAssembly` 会把没有明显辅助语义的文字保守分类为 `BODY`。这只是为了诊断展示，并不能证明它已经属于某一条聊天消息。

交接包的 `MessageAssembler` 要求：

- 消息边界已经确认；
- 片段由可靠规则或用户选择确认；
- 片段确实位于该消息边界内；
- 只整理正文，不猜作者、时间或图片语义。

影响：如果把当前 BODY 直接当作已确认正文，可能把作者、时间、导航、语音时长或其他消息混入翻译请求。

解决方式：先完成消息边界和人工回退设计，再启用 `MessageAssembler`。在边界未确认前，只能显示候选，不能发送给翻译 Provider。

### 卡点 6：真机证据还不足以关闭 P0.5/M2/M3

已有证据说明截图、节点长文和日文 OCR 通路可用，但尚未完整验证：

- 同屏重复消息是否保留；
- 长文边缘是否截断；
- 节点正文和作者/时间是否稳定分区；
- OCR 候选勾选是否会丢失滚动位置或选择；
- 切页、滚动、锁屏、关闭和服务重启后旧结果是否失效；
- 图文混排和语音消息是否会串入正文；
- 字体放大、窄屏和方向变化下卡片是否仍可关闭。

影响：目前可以说“探针和部分链路可用”，不能说“正文提取已经长期稳定”，更不能跳过正文门槛直接开发翻译。

解决方式：在协调器和正文候选流程稳定后，由用户配合做少量、分阶段真机验证；每次只验证一个明确目标，不要求一次完成全部测试。

### 卡点 7：Windows 核心测试脚本不能按文档直接运行

`verify-core.ps1` 是 UTF-8 无 BOM，Windows PowerShell 5.1 会把其中中文字符串按本地代码页读取，造成解析错误。手工执行同等编译和测试步骤已经通过，因此不是 Java 核心代码失败。

影响：另一台 Windows 电脑照 README 复制命令时可能直接报错，无法形成可重复验证。

解决方式：后续修复脚本编码兼容或明确要求使用能正确读取 UTF-8 的 PowerShell 版本，并分别验证“交接副本”和“主工程正式 domain 路径”。

## 六、建议的逐步优化顺序

### 阶段 0：补齐交接事实

目标：确保接入的确实是完整、最终的审核版本。

动作：

1. 恢复两份缺失文档。
2. 确认长期方案对应关系。
3. 确认 v0.2 是否为最新交接包。
4. 复核全部 SHA-256。
5. `handoff/core_modules` 候选目录已建立；补齐两份文档后再复核全包摘要，不把它当第二个 Android 工程。

通过条件：阅读入口完整、文件摘要匹配、主方案只有一个明确入口。

### 阶段 1：统一唯一生命周期

目标：让截图、OCR、关闭、页面失效和未来翻译都由一个协调器管理。

动作：

1. 先补足协调器行为测试。
2. 把生产服务从 `RequestGate` 分步迁移到 `CaptureCoordinator`。
3. 覆盖重复点击、关闭、切页、锁屏、销毁和迟到回调。
4. 搜索旧调用，确认退役后再删除旧实现。

通过条件：生产服务只使用一个生命周期状态源；所有已启动物理任务真实结束后才开放下一次请求。

### 阶段 2：统一数据契约和诊断证据

目标：接入 domain 模型，同时不丢失现有采集证据。

动作：

1. 建立 Android 采集模型到 domain 模型的单向适配。
2. 保留 provenance、warnings、decisionReason、原始文字和人工选择。
3. 统一 PageToken、messageId、fragmentId 和坐标语义。
4. 编译并运行现有 Probe 测试与 Core 39 项测试。

通过条件：不存在未经测试的双向转换；诊断信息不静默丢失；旧 UI 仍可展示候选。

### 阶段 3：确认消息边界和正文

目标：把“正文候选”升级为“可明确归属到某条消息的已确认正文”。

动作：

1. 使用合成页面覆盖重复、长文、时间、语音、图片和未知结构。
2. 对无法可靠自动判断的片段保留人工选择。
3. 只有边界确认后才调用 `MessageAssembler`。
4. 真机验证至少短消息、多条同屏、长文和图文混排。

通过条件：无未提示的整块遗漏、误去重或跨消息串联；UNKNOWN/OCR 候选不会自动变成已确认正文。

### 阶段 4：接入未激活的翻译 domain

目标：先接入请求、结果、风格和校验契约，不连接真实厂商。

动作：

1. 接入 `StyleProfile`、`TranslationRequest/Result/Validator` 和 `SymbolProtector`。
2. 使用本地假 Provider 测试请求绑定、页面过期、空返回、符号丢失和至多一次重试策略。
3. 确认不会记录含私人正文的 `toString()`。

通过条件：无网络也能完整验证翻译生命周期；过期结果和身份不匹配结果不能显示。

### 阶段 5：经用户确认后接入 DeepSeek

目标：在正文和本地契约稳定后，增加真实文本翻译。

动作：

1. 查阅最新官方文档和账户实际能力。
2. 增加最小网络权限、手机端 Key 输入和安全清除。
3. 将真实请求句柄纳入唯一协调器。
4. 加入超时、取消、限流、费用控制和脱敏日志。
5. 小样本验证自然度、称呼、语气、换行和符号。

通过条件：请求身份、页面身份、风格版本和符号校验全部通过；用户能控制 Key 和费用；失败不会泄露正文或阻塞后续请求。

### 阶段 6：日常使用验收

目标：确认不是“能演示”，而是能长期使用。

动作：

1. 验证卡片滚动、拖动、收起和大字体。
2. 验证断网、慢网、切页、锁屏和服务重启。
3. 分别记录代码、JVM 测试、APK、安装和真机状态。
4. 根据真实使用反馈逐步调整术语和文风版本。

通过条件：关键失败都有明确提示和恢复路径；没有第二套生产状态机；没有未经允许的图片上传或私人内容持久化。
