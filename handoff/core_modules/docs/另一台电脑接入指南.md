# 另一台笔记本：接管、依赖检查、分步接入

## 1. 如何衔接两个会话

本会话负责准备模块和证据。另一台笔记本的 Luna 必须在你的实际主工程目录中运行，才能修改那里的文件、运行 Gradle 和连接真机。GitHub 传递源码与文档，不同步未提交文件、聊天记忆、Android SDK、API Key 或签名私钥。

建立唯一事实来源：主工程的 Git 仓库和一个明确的完整提交 SHA。审核包 README 自述为 1302cd6；本电脑没有该 Git 仓库，不能证明与主仓库该提交完全相同。主工程若有更新，以主工程现有功能和测试为起点，逐项核对审核问题是否仍存在。

用户尚未提供 GitHub 仓库地址，也未提供另一台电脑操作系统；因此本包没有推送、拉取或修改那台电脑。下列路径以主工程根目录为基准，不依赖本机用户名或下载目录。

## 2. 可直接交给 Luna 的首轮任务

> 请在当前打开的 Android 主工程中工作。先阅读原有 AGENTS.md、用户确认的长期稳定版开发总方案，以及 handoff/core_modules/README.md 和其链接文档。不要假定你已获得另一会话记忆。
>
> 先检查 Git 分支、完整提交 SHA、未提交修改、JDK/Gradle/AGP/SDK 版本；不要输出密钥、正文、私有仓库认证 URL。对比审核0914快照与当前采集、状态机、OCR 及构建实现，生成 docs/接管基线.md，标明审核问题仍存在、已解决或尚待核实。保留我的已有代码和修改。
>
> 按本文阶段 A→B→C 推进：先使原有工程可复现构建，再导入与测试纯 Java 模块，最后只接入一条已经确认边界的文字消息。已有同名类必须比较合并，不覆盖。不建立第二套 App 或第二个总协调器。每阶段编译测试后更新 docs/迁移状态.md，列出实际修改文件、命令、结果和真机待测项。
>
> 本轮不连接真实付费 API、不上传聊天图片。完成阶段 C 所需真机证据若暂缺，继续能独立完成的逻辑测试，并清楚列出需要我执行的手机操作。不要把未接入、未构建或未真机验证的项目标为完成。

这段任务有意限定首次接入范围。完成首次接入后，再按总方案逐步授权 API、文风和悬浮层开发；不要让一次提示词触发 15 天计划所有功能同时修改。

## 3. 接管时先核对这些证据

在主仓库执行只读检查：

```text
git status --short
git branch --show-current
git rev-parse HEAD
git log -5 --oneline
java -version
javac -version
```

Windows 用 .\gradlew.bat --version；macOS/Linux 用 ./gradlew --version。如果对应 wrapper 缺失，先按第 4 节修复，不使用来历不明的全局 Gradle 顶替。Gradle wrapper 首次启动可能下载其声明的分发包，需要网络与缓存写入权限。

另检查这些文件的实际内容（含已有锁定文件、版本目录）：

- settings.gradle.kts：模块名、仓库源。
- build.gradle.kts：AGP 版本、强制依赖约束。
- app/build.gradle.kts：SDK、语言版本、依赖、签名。
- gradle/wrapper/gradle-wrapper.properties：Gradle 版本与下载地址。
- gradle.properties：本机绝对路径覆盖项。
- app/src/main/AndroidManifest.xml：服务注册、权限、前台服务声明。
- .gitignore、scripts/verify-probe-logic.ps1 及现有测试配置。

不要输出 local.properties、凭据文件或完整环境变量列表。只记录 SDK/JDK 路径是否有效及必要的版本信息。未提交改动属于用户，先记录边界，不 reset、不强制 checkout、不擅自清空。可以在确认的工作基线上建立开发分支；若用 worktree，明确未提交改动不会自动带入。

docs/接管基线.md 必须写：主仓库完整 SHA、分支、是否有未提交改动、系统与工具版本、原逻辑测试和原 APK 构建结果、与审核快照的差异、仍存在的问题和具体源码路径。不把 1302cd6 当作已核实的新基线。

## 4. 依赖：先复现，再最小修复

| 项目 | 审核快照实际声明 | Luna 的处理 |
|---|---|---|
| Java 源码 | 17 | 保持语言级别 17；运行 Gradle 的 JDK 以所用 AGP/Gradle 官方兼容表为准 |
| AGP | 9.0.1 | 先确认主工程实际版本；不要为“最新”而自动升级 |
| Gradle | 9.1.0 | 使用仓库 wrapper；核对与 AGP 的兼容关系 |
| Android SDK | compile/target 36，min 34 | 配置本机 SDK，按实际构建要求安装所需组件；不要降低 minSdk 掩盖截图 API 问题 |
| 日文 OCR | com.google.mlkit:text-recognition-japanese:16.0.1 | 暂保留已有依赖；核心接入不要求升级 OCR |
| Kotlin stdlib | 根脚本强制 2.2.0 | Java 工程也有该约束；先查依赖树，不能看到 Java 就直接删除 |
| AAPT2 | Windows D 盘绝对路径覆盖 | 若主工程仍有且失效，移除机器专用 override，让 AGP 解析其匹配工具；保留修改证据 |
| Wrapper 脚本 | 快照仅 gradlew.bat | 从主仓库/可信官方同版本生成完整 wrapper；不覆盖 properties 改版本；检查 jar 来源/校验值及 Unix 执行权限 |
| Debug 签名 | 指定根目录 debug.keystore，但快照不含 | 查主工程是否已有私钥；保留现有可用签名。审核副本可用默认 debug 签名，不在仓库添加私钥 |

本次核心包没有新 Maven 依赖，不需要 HTTP 库、Room、依赖注入框架或另一个 Gradle module。不要为了目录整齐一次性增加许多框架。

可用官方核对入口：

- https://developer.android.com/build/releases/gradle-plugin
- https://docs.gradle.org/current/userguide/compatibility.html
- https://docs.gradle.org/current/userguide/gradle_wrapper.html
- https://developers.google.com/ml-kit/vision/text-recognition/v2/android

上述链接用于另一台电脑接入当时复核版本；本次没有声称完成该电脑依赖兼容验证。

修改构建配置时，一次解决一个已重现问题，重跑同一失败命令。不要把升级 Gradle、改签名、升级 OCR 和重写 Service 放在同一次提交里。

API 依赖留到文本翻译阶段：先核对 DeepSeek 当前官方 API、账户模型和图像支持，再选择 SDK/HTTP 实现、超时、取消和错误码处理。模型名字和“支持 Vision”不能沿用旧文档未经核实的描述。用户同意可上传局部图片，但产品仍需显示裁剪预览及本次确认。

## 5. 分批迁移与验收

### 阶段 A：保住原工程

1. 执行第 3 节检查，写接管基线。
2. 运行原 ProbeLogicSelfTest 及原有测试。
3. 用仓库 wrapper 运行 :app:assembleDebug；记录失败根因或 APK 路径。
4. 只修阻塞构建的本机依赖/路径，不改变识别逻辑。

验收：原工程能编译；若原先就失败，有明确失败日志与最小修复。建立可恢复基线提交。签名若改变，旧 APK 可能不能直接覆盖安装，不能擅自卸载导致配置丢失。

### 阶段 B：导入核心模块，仍不改变用户可见行为

1. 在 handoff/core_modules 运行本包独立自测。
2. 搜索主工程是否已有 PageToken、TextFragment、ChatMessage、StyleProfile、TranslationProvider 等同名或同职责实现。
3. 不存在的类移动到 app/src/main/java/com/fanli/sakurazakatranslator/domain；已有实现逐项比较、合并接口与调用方。保留单一正式源码位置。
4. 用本包脚本的源码目录参数，测试刚导入的生产代码；再运行原测试和 :app:assembleDebug。

验收：测试编译的是 app 内实际源码；没有 duplicate class；原采集页面仍可用；新增代码没有 Android 或 HTTP 依赖。接口若与本包不同，同步修改测试/模块地图并说明原因。

### 阶段 C：接入一条已确认聊天消息

1. 根据真实节点的 parentId、childIndex、traversalIndex、窗口和矩形，确认一条聊天气泡。先允许手动选择，不能假设所有 Role.BODY 都是聊天。
2. 仅在这一入口转换旧 ProbeModels 到新模型，建议把转换放 capture 包内独立适配类。不要同时大改旧模型的所有使用点。
3. 无边界、不完整边界或无法确认归属时保留候选，禁止把 boundaryConfirmed 写死为 true。
4. 把已确认的 ChatMessage 交给 MessageAssembler；显示本地整理结果用于验证，不调用付费 API。
5. 测试乱序勾选、多行、同文重复、按钮/时间/语音时长、图片候选、不同作者切换。空 sourceText 不发请求。

验收：普通消息原文与符号不变、顺序正确，导航和语音控件不进入正文；完成一次实际设备节点检查。未取得设备节点证据时只能标记“纯逻辑通过、接入待确认”。

### 阶段 D：统一流程，再加翻译与显示

以主工程最新实现为准。审核快照中 Service 用 ProbeLogic.RequestGate，CaptureCoordinator 未接入。迁移时替换生产调用，使一个负责人管理请求序号、页面代次、物理任务占用、取消和资源释放。ProbeLogic 中的资源租约/纯工具可继续复用，不能把整个文件直接删掉。

必须证明这些顺序：

- 启动截图前页面有效；截图成功回调启动 OCR 前再次有效。
- OCR/Vision 完成准备启动下一任务前再次有效。
- 发起翻译前有效，收到结果后且显示前仍有效。
- 锁屏/切人物/离开目标页立即失效、隐藏悬浮层；物理任务未结束时不因逻辑失效错误释放占用。
- 旧回调只能释放自己的资源，不能释放新请求、重置新状态或提交结果。

TranslationValidator 只比较请求与结果，不掌握当前屏幕。总协调器必须另行检查实时 PageToken。符号失败重试至多一次；上下文已经失效时直接丢弃，不再重试。网络超时/限流策略单独定义，避免 SDK 和总协调器各重试一次造成调用放大。

验收：模拟延迟回调、取消后再点、锁屏和销毁均不启动后续 OCR/HTTP。再逐项接 DeepSeek、风格配置、悬浮层，不同时切换全部入口。

## 6. 真实依赖与文件怎么交给 Luna 管

Luna 每阶段必须更新一个状态表（docs/迁移状态.md），至少包含：阶段、基线 SHA、实际改动文件、当前生产调用入口、已退役旧入口、测试命令与退出码、APK 版本、真机证据、下一步。计划中的文件写“未创建”；不得把文件存在等同于已接入。

每次交接固定给四样东西：仓库、分支、完整 SHA、下一阶段。另一台电脑先比较自身状态，避免盲目 git pull；有未提交改动先处理合并边界。

不覆盖主工程根 AGENTS.md。若需要让每次新会话自动发现规范，将以下指向合并进原 AGENTS.md 的合适位置：

> 本项目的功能约束见用户确认的长期稳定版开发总方案；当前迁移入口为 handoff/core_modules/README.md。修改前阅读 docs/接管基线.md 和 docs/迁移状态.md，以最新主工程代码和验证结果为依据。审核快照是参考，不得整体覆盖主工程。

## 7. 提交与回退

每个可验证阶段做一个清晰提交，记录完整 SHA。提交前检查 git diff --check、git diff --stat 和实际差异，确认没有私人数据；按明确文件路径暂存，不盲目 git add .。

已推送的错误提交优先用 git revert 对准确提交撤销，再运行同一批测试。尚未提交的修改用可审阅的反向补丁逐文件恢复自己的变更；不使用 git reset --hard 清掉用户工作。回退源码后重建 APK，并考虑签名和数据兼容；不把换旧 APK 当作无条件可行。

## 8. 真机时间点与 15 天计划

约 15 个工作日是规划，不是已验证的工期保证。另一个工程差异、API 能力和设备布局可能影响它。

- 第 1 天附近：原工程安装/权限/截图冒烟检查。
- 第 2～4 天：节点边界和 OCR 裁剪短检查，决定适配规则。
- 第 7～8 天：译文位置、滚动和字体大小短检查。
- 第 10 天：局部图片预览、确认/取消、实际 API 能力检查。
- 第 15 天：集中约一天的完整真机矩阵；失败项修复后需要对应复测。

如果“真机测试一天”是指全部设备接触时间，建议把这一天的工时分散到上述节点；若只能最后一天接触手机，前期消息定位只能是假设，15 天结束时不能保证稳定版。少量早期验证能显著减少最后返工。
