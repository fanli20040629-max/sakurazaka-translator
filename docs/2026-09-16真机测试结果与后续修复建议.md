# 2026-09-16 真机测试结果与后续修复建议

## 1. 结论

本轮 `0.3.1-probe-review` / 4 已完成桌面构建验收，并由用户在目标 App 页面进行了首轮真机操作。三份脱敏后的视觉证据表明：指定窗口截图、日文 OCR、候选列表和长结果展示链路能够实际运行；至少一个样本显示截图尺寸为 `1080×2340`，采集到候选时显示的 OCR 总耗时为 `283ms`。

本轮不能判定 P0.5 整体通过。正文识别属于“部分通过”，主要确认了四类问题：

1. 彩色 Emoji/装饰符号不能可靠识别，已观察到句尾 Emoji 被错误替换为普通字符 `9` 或汉字 `米`，不是单纯漏字。
2. 作者、日期时间、导航字符和媒体辅助文字仍作为 OCR 候选出现，需要用户手动排除。
3. 日期与时间可能粘连，例如缺少应有空格；这说明 OCR 原文不能直接当作结构化元数据。
4. 长消息仍按 OCR 行拆成多个“片段”，尚未形成有证据的消息边界。

因此，当前 APK 可以继续用于采集证据和验证交互，但不能直接接入翻译 API，也不能宣称已经实现完整消息、符号保真或自动元数据过滤。

## 5. 三组视觉证据的脱敏观察

### 5.1 样本 A：多条消息、媒体和语音混合页面

- 截图接口返回成功，显示 `1080×2340`。
- 结果卡片显示 OCR 总耗时 `283ms`。这是一次端到端样本，不是纯 OCR 基准，也不能代表平均值或上限。
- 作者、日期时间、导航符号和媒体覆盖文字分别成为候选，说明全窗口 OCR 正常，但正文区域尚未限定。
- 两处句尾 Emoji/装饰符号没有保真：一处变成 `9`，另一处变成 `米`。
- 该现象证明当前问题是“错误替换”，后续不能简单删除所有数字或汉字来修复。

### 5.2 样本 B：单条长消息页面

- 长段日文被识别为多个候选行，主要文字可阅读。
- 作者和日期时间进入候选，且日期与时间之间出现粘连。
- 一条可见消息被拆成多个 OCR 行；当前 UI 正确称其为片段，但尚无消息气泡分组。
- 截图没有完整展示长消息首尾对照，因此不能证明零截断。

### 5.3 样本 C：多条较长消息页面

- 不同位置的多个段落均产生候选，整体顺序与屏幕纵向位置大体一致。
- 句号、顿号和感叹号等普通日文标点在可见样本中多数保留。
- 长句继续按视觉行拆分；作者和时间会在正文片段之间出现。
- 结果支持继续开发“位置映射与分组”，但不支持宣称消息边界已经完成。

## 6. 问题判断

### 6.1 Emoji 错误的性质

当前 OCR 使用 bundled Japanese ML Kit，对日文、拉丁字符和部分普通标点有效，但彩色 Emoji、组合 Emoji、变体选择符、ZWJ 序列和装饰图形不属于可靠识别范围。光栅化后的图形可能被分类为视觉相近的普通字符，因此会出现 `9`、`米` 等错误替换。

这不是通过一张字符替换表就能安全修复的问题：

- 页面中真实的 `9` 和 `米` 也可能是正文。
- 同一个 Emoji 在不同字体、尺寸和背景下可能产生不同 OCR 输出。
- OCR 没有输出时，无法仅凭空缺确定原来是哪一个 Emoji。
- 盲目根据上下文补 Emoji 会伪造用户原文。

### 6.2 元数据混入的性质

OCR 当前针对整个目标窗口执行，每条 OCR 行统一作为 `MEDIA_CANDIDATE`。它没有目标 App 的消息区域、作者区域、时间区域和导航区域模型。因此作者/时间出现并不是候选状态模块失效，而是区域分类和消息结构尚未实现。

### 6.3 行片段不等于消息

ML Kit 返回的是块和行。视觉换行可能把一条消息拆成多个候选；相邻两行也可能属于不同消息。仅凭文本相似、垂直距离或换行符强行合并都会产生误分组。消息分组必须结合位置、气泡边界、节点层级、作者/时间锚点和页面类型证据。

## 7. 建议解决方案

### 7.1 P0：建立节点原文与 OCR 的保真合并

目标：无障碍节点能够提供原文时，以节点字符串作为字符真值；OCR 只补充节点取不到的图片文字，不覆盖节点中的 Emoji、符号或换行。

建议实施：

1. `NodeTreeReader` 保留节点 `text` / `contentDescription` 的原始 Java 字符串、来源和屏幕边界，不做 Unicode 归一化或字符替换。
2. `ProbeModels.TextFragment` 明确保存 `rawText`、来源、边界、pageToken、匹配状态和警告；展示文本与原始文本分离。
3. `TextAssembly` 新增节点片段与 OCR 行的空间匹配。先使用边界重叠和阅读顺序，再使用保守文本相似度辅助；不能只按文本内容去重。
4. 节点与 OCR 指向同一区域且节点含有更完整符号时，正文候选使用节点 `rawText`，OCR 只保留为诊断来源。
5. 找不到可靠对应关系时，节点和 OCR 保持独立候选，不自动融合。

验收标准：节点原文包含 Emoji 时，最终确认片段的 Unicode code point 序列必须与节点原文完全一致；OCR 的 `9`/`米` 不得覆盖节点中的真实符号。

### 7.2 P0：对无法恢复的符号明确降级

当页面只提供截图、节点没有原文时，不应猜测 Emoji。建议：

- 给 OCR-only 片段增加 `SYMBOL_UNVERIFIED` 或等价警告。
- UI 显示“图片文字可能缺少 Emoji/装饰符号”。
- 提供用户编辑或确认原文的入口，再生成 TranslationRequest。
- 保留 OCR 原始输出供核对，不在后台静默替换。
- 在翻译请求中携带警告，禁止把未确认片段标成“逐字保真”。

### 7.3 P1：元数据和非正文分类

建议按证据强度分层：

1. 先使用目标页面已确认的区域边界和节点角色。
2. 时间格式、日期格式、语音时长只能作为辅助特征，不能单独决定删除。
3. 作者、时间、导航、按钮和媒体标签进入独立分区，默认不加入待翻译正文。
4. 证据不足的内容保持 `UNKNOWN`，交给用户选择。
5. 日期时间粘连只用于显示诊断；在没有可靠结构证据前，不修改 OCR 原文插入空格。

### 7.4 P1：真正的消息边界

- 先建立目标页面布局版本和消息气泡区域证据。
- 使用同一气泡/节点父级、水平范围、垂直连续性、作者/时间锚点综合分组。
- 同文不同位置必须保留，不能按字符串去重。
- 多行合并时保留原始行列表、换行策略和来源 ID，允许回退到未分组片段。
- 无法证明属于同一消息时不合并。

### 7.5 P1：候选 UI 改进

- 显示来源：节点、OCR 或节点+OCR。
- 对 Emoji/符号未验证、元数据疑似、边界不确定分别显示警告。
- 支持编辑确认后的文本，但同时保留不可变的 OCR 原始值用于诊断。
- 继续保持 OCR 候选默认不选；页面变化后清空编辑和选择状态。

## 9. 建议先写的回归测试

1. 节点字符串包含单码点 Emoji，输出 code point 完全一致。
2. 节点字符串包含变体选择符、肤色修饰、ZWJ 组合、旗帜和 keycap 序列，不能截断或拆坏。
3. 同一区域节点为真实 Emoji、OCR 为 `9` 或 `米`，最终候选必须保留节点原文并标记 OCR 差异。
4. 只有 OCR、没有节点时，不猜 Emoji，并出现符号未验证警告。
5. 真实正文包含数字 `9` 或汉字 `米` 时不得误删。
6. 作者、日期、时间、语音时长和返回按钮按证据进入非正文分区。
7. 日期时间粘连样本保留原始值，不擅自插空格。
8. 一条多行消息在有气泡证据时正确分组；无证据时保持多个片段。
9. 相同文字出现在不同位置时全部保留。
10. 反向勾选后，确认片段仍按屏幕顺序输出。
11. 关闭、切页、锁屏后，编辑状态、选择状态和迟到 OCR 结果全部失效。

## 10. 下一轮真机验收矩阵

完成修复后使用新的 versionCode 和 APK 哈希，至少复测：

- 含单个 Emoji 的节点正文。
- 含多个连续 Emoji、ZWJ 和变体选择符的节点正文。
- 节点可读、OCR 错误替换的同一区域。
- 只有图片文字、节点不可读的页面。
- 真实包含 `9` 和 `米` 的正文，防止误修复。
- 作者、时间、语音时长、导航和媒体标签混合页面。
- 单条长消息、多行消息、多条同屏、同文不同位置。
- 反向选择、全部取消、关闭后重新取字。
- OCR 中关闭、切页、切 App 和锁屏。
- 连续约 20 次取字，记录崩溃、任务叠加、耗时和内存趋势。

通过标准：

- 有节点证据的 Emoji 和符号逐 code point 保真。
- 无法恢复的 Emoji 明确提示，不生成猜测字符。
- OCR 错误不覆盖更可靠的节点原文。
- 作者/时间等默认不进入正文，但不在证据不足时静默删除。
- 消息分组有可追溯来源；失败时可安全回退为片段。
- 页面失效后旧结果、编辑和选择均不会重新出现。

## 11. 给下一位开发者的执行顺序

1. 先读取本报告、`project_state.md`、`本轮优化验收与交接.md` 和 `当前代码审核与改进方案.md`。
