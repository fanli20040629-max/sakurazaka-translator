# Sakurazaka46 MSG 中文翻译助手
# 长期稳定版开发总方案

版本：v1.0
计划周期：约 15 个工作日
目标用户：先满足个人使用，同时保留分享给其他用户的能力
目标语言：简体中文
首要原则：准确性 > 美观性 > API token 消耗 > 响应速度

## 一、这份文档要解决什么问题

现有项目已经证明了三件事：

1. 可以通过 Android 无障碍服务识别目标应用窗口。
2. 可以通过指定窗口截图和本地日文 OCR 获得文字。
3. 可以在屏幕上显示一个浮动结果卡片。

但现有版本还是“取字和调试探针”，不是完整的翻译应用。它会把作者、时间、正文、导航、按钮、语音控件和图片文字混在一起，也不能把译文稳定地放回对应的聊天消息附近。

本方案的最终目标是：

> 打开 Sakurazaka46，点击浮窗，应用识别当前可见的聊天消息，翻译成自然的简体中文，并将中文显示在对应日语消息附近。原文、换行、Emoji、波浪号、爱心和偶像个人语气都必须保留。

图片中的日文先在手机本地 OCR。只有本地结果不可靠，并且用户确认后，才将局部图片发送给 DeepSeek Vision 重新识别。

## 三、面向用户的完整流程

### 3.1 用户看到的流程

1. 打开 Sakurazaka46。
2. 确认当前页面是已配置的聊天页面。
3. 点击浮窗。
4. 应用读取当前可见聊天消息。
5. 普通文字先进入翻译。
6. 图片消息先尝试本地 OCR。
7. OCR 结果不可靠时，显示局部图片预览和“发送给 DeepSeek 重新识别”按钮。
8. 翻译完成后，中文显示在对应日语消息下方。
9. 用户可以展开原文、隐藏译文或重新翻译。

### 3.2 数据流程

聊天页面 → 页面身份确认 → 消息识别 → 消息分类 → 本地 OCR → 低置信度筛选 → 可选 DeepSeek Vision → DeepSeek 中文翻译 → 结果校验 → 悬浮层定位 → 用户查看。

## 四、核心数据结构

代码必须以消息为中心，而不是以屏幕文字为中心。

### 4.1 PageToken

保存当前页面身份：

- targetPackage
- windowId
- pageEpoch
- captureTime
- 可选的页面轻量指纹

任何截图、OCR、Vision 或翻译结果提交前，都必须检查 PageToken 是否仍然有效。

### 4.2 ChatMessage

每条聊天消息至少包含：

- messageId
- authorId
- authorName
- timestamp
- messageBounds
- textFragments
- imageRegions
- mediaType
- sourceConfidence
- translationState

### 4.3 TextFragment

每段文字包含：

- fragmentId
- rawText
- source：节点文字、节点描述、本地 OCR、云端 Vision
- bounds
- symbols
- lineBreaks
- confidence
- selected

### 4.4 TranslationResult

至少包含：

- messageId
- sourceText
- translatedText
- preservedSymbols
- provider
- model
- styleProfileVersion
- confidence
- needsReview
- createdAt

## 五、消息识别方案

### 5.1 识别优先级

1. 无障碍节点结构。
2. 节点父子关系和边界。
3. 作者名和时间的相邻位置。
4. 图片或语音控件的类型。
5. OCR 只作为图片文字补充。

不能把整个窗口截图直接 OCR 后作为最终聊天文本。

### 5.2 默认排除内容

- 顶部页面标题。
- 返回、菜单、邮件等按钮。
- 底部导航。
- 登录页提示。
- 邮箱和密码说明。
- 语音播放按钮、进度条和下载按钮。
- 与聊天消息没有空间关系的装饰图。

### 5.3 识别失败时

如果无法确定作者或消息边界：

- 不猜测。
- 使用“未识别消息”状态。
- 允许用户手动选择当前人物。
- 仍保留原始节点和截图证据。

## 六、两位偶像的文风系统

第一版只需要两位偶像，但核心代码不能写死她们的姓名或规则。

### 6.1 风格档案分层

每位偶像有三层：

1. 通用翻译规则：所有用户共享。
2. 公开文风档案：由 Blog 分析生成。
3. 用户个人偏好：只保存在用户自己的配置中。

Blog 文风和 MSG 文风必须分开：

- Blog 通常更完整、更正式。
- MSG 通常更短、更口语化、更常使用 Emoji 和波浪号。

### 6.2 风格档案内容

- 自称和常见称呼。
- 人名、昵称和活动名。
- 常用句尾。
- 礼貌程度。
- 句子长短。
- 常用 Emoji、爱心和波浪号。
- 感谢、道歉、想念、鼓励等场景表达。
- 禁止添加的亲密称呼。
- 翻译示例。

### 6.3 不懂日语时的使用方式

用户不需要维护日语规则。应用应把分析结果转换成中文说明，例如：

“这位偶像的 MSG 通常比较温柔、口语化，波浪号表示轻松或撒娇，翻译时不宜使用过于正式的中文。”

用户只需要确认中文说明是否符合自己的感觉。

### 6.4 Blog 导入流程

1. 用户提供 Blog 文本或导出文件。
2. 本地清理网页导航、标题和重复内容。
3. 将 Blog 分批提交给风格分析任务。
4. 生成中文风格档案、词典和少量示例。
5. 用户确认档案。
6. MSG 翻译时再用真实聊天样本校正。

整篇 Blog 不应在每次翻译时重复发送。

## 七、DeepSeek 接入方案

### 7.1 文本翻译

DeepSeek 官方 API 当前提供 OpenAI 兼容接口，官方 Vision 文档列出的图片模型为 deepseek-flash。模型名、价格和可用性在开发时必须从官方文档重新确认，不能依赖旧资料。

翻译请求必须包含：

- 当前偶像身份。
- sourceText。
- 已提取的符号。
- 风格档案摘要。
- 少量相似示例。
- 输出语言为简体中文。
- 输出结构要求。

### 7.2 图片 Vision

DeepSeek 官方支持 JPEG、PNG、GIF、WebP，图片可通过 base64、外部 URL 或 Files API 发送。

本项目默认使用局部图片 base64：

- 不需要建立长期文件。
- 适合一次性局部裁剪。
- 不发送整屏。
- 发送前可以在本地完成裁剪和预览。

图片策略：

- 低置信度才请求 Vision。
- 小字和符号优先使用 original 或 high。
- 不默认使用 low。
- 单次只发送当前需要确认的局部图片。
- 不把图片放进 system message；规则放在 system，图片放在 user 内容中。

### 7.3 API Key 和分享模式

个人模式：

- API Key 存入 Android Keystore 保护的本地存储。
- 用户自己承担 API 费用。
- 不把 Key 写入源码、GitHub 或 APK 常量。

分享模式：

- APK 不保存公共 API Key。
- 通过后端代理调用 DeepSeek。
- 后端负责限流、额度、日志脱敏和密钥保护。
- 用户可使用自己的账号或由服务端提供受控额度。

代码必须使用 Provider 接口，DeepSeek 只是第一种实现。未来可以替换其他翻译服务，不修改消息识别和 UI。

## 八、翻译质量规则

翻译优先级：

1. 事实和消息对应关系。
2. 原文含义。
3. 符号、Emoji、换行和人名。
4. 偶像个人语气。
5. 中文自然度。
6. token 和速度。

模型不允许：

- 删除原文符号。
- 添加原文没有的暧昧语气。
- 把普通礼貌改成过度正式的公告。
- 把不确定的人名强行翻译。
- 把导航或按钮翻译成聊天内容。

程序必须在模型返回后检查：

- Emoji 是否保留。
- 波浪号和爱心是否保留。
- 换行是否保留。
- messageId 是否正确。
- 返回格式是否正确。

检查失败时，自动重试一次；仍失败则显示原文并标记“需要确认”。

## 九、中文悬浮层设计

默认展示方式：原日语消息下方显示中文气泡。

要求：

- 中文气泡绑定 messageId。
- 根据 messageBounds 定位。
- 跟随原页面滚动。
- 页面切换、锁屏、服务中断时清除。
- 中文过长时在气泡内部换行。
- 原文可以展开查看。
- 技术详情默认折叠。
- 不显示 NODE_DESCRIPTION、坐标和内部 ID。

如果无法可靠定位单条消息，回退为“当前页面翻译卡片”，并明确提示用户当前是整体结果，而不是逐条贴合。

## 十四、非专业用户应该如何判断进度

你不需要阅读代码，只需要在每个节点看三个问题：

1. 程序有没有识别对消息？
2. 中文有没有放在正确消息旁边？
3. 原文语气和符号有没有被破坏？

如果第一项不对，先修消息识别；
如果第一项对、第二项不对，修悬浮层定位；
如果前两项都对、第三项不对，修提示词、个人风格档案和符号保护。

不要在消息识别还不准确时，用更强的模型掩盖问题。模型越强，错误输入可能产生越像真的错误翻译。
